# v3.6.2

本版专治一类性能病：**进入某个页面时，界面长时间无响应**。有用户实报「进入星运台时卡死」，排查确认卡的是界面线程、且卡在「进入页面」这一步，不是排盘慢。

- 三处页面的重可视化引擎改为按需加载(本版核心):
  - **病因**:页面组件**静态**引入了 3D / 图表组件,打包器遂把整个引擎变成该页的同步依赖 —— 只要进这个页,就得先把整个引擎解析完,哪怕你从不打开那个 3D 子页签。配置一般的机器上足以让主线程长时间无响应。
  - **星运页(用户实报的那处)**:主限天球背后是 three.js(引擎包 862KB + 天球自身 90KB)。而该页默认停在「主限法」表格,二十多个子页签里只有「主限天球」一个用得着 3D —— 从不看天球的用户,每次进星运页都要先白等这份解析。该页还是空闲预载队列里优先级最高的一个,连「从不进星运页」的用户都可能在后台空闲期吃到它。
  - **节气页**:3D 盘背后是 three.js 加七个附加模块、两个大字体与模型资产,量级比星运页更大。
  - **玄学史页**:天象与地图两个子页背后是 echarts(比 three 还大);而该页主体是概览,十来个子页里只有这两个要图表。
  - **改法**:三处都改为「点开才加载」+ 空闲预热 —— 不打开就零成本,真去点时通常已经就绪,体感不退步。天球/3D盘/天象/地图的功能、动画、交互与扩展面板全部与改版前一致。
  - 顺带清理 3D 星盘页的一处死代码:其盘型切换在构造时就被固定,那个分支永远不成立,但它仍把主限天球引擎白白拖进 3D 包 —— 删除后引擎包由 862KB 降到 713KB。

- **启动首屏净省 1.1MB —— 这条所有人都受益,不限于上面三个页面**:
  - 上面把图表引擎改懒加载之后,复核打包产物才发现它**根本没省到**:图表引擎与另一个叫 d3 的库被编在同一个共享包里(合计 1228KB),而 d3 是**画星盘用的基础设施**(全仓一百多个文件在用)、软件一启动就需要 —— 于是图表引擎被它捎带着,每个用户开机就得下载并解析,哪怕从不进玄学史页。
  - 二者用途宽窄天差地别,已拆成两个包:基础设施那份 129KB(启动即取,正确),图表引擎那份 1132KB(只有真去点天象/地图时才取)。**启动阶段少 1.1MB 的下载与解析。**
  - 这类问题比原病灶更隐蔽:引擎明明规规矩矩待在共享包里、页面也确实改成了懒加载,单看代码全都对 —— 只有直接翻打包产物、看「启动那一批到底拉了哪些文件」才现形。已就此加了第五道护栏(判据只认产物、不看配置也不看包名,谁改回去都当场拦下)。

- **增量更新真正生效了 —— 此前一直是「名为增量、实为全量」**:
  - 打包完成后做更新链路实测,软件报「本次需下载 690MB,复用 0%」。追查发现:增量更新靠「比对部件指纹,一样就不下」来省流量,而**打包过程本身不可复现** —— 同样的内容重打一次,指纹就变。于是每个部件都被判成「变了」,每次更新每个人都在全量重下。
  - 实锤:上一版已装的星历数据与本版新包**逐文件内容完全一致**(158 个文件,内容摘要分毫不差),部件指纹却不同。
  - 两个与内容无关的指纹漂移源,都已修:压缩包头部写了打包时刻;打包前目录的时间戳被拷贝过程刷新(文件本身的时间戳其实是保留好的)。只归一目录时间戳、不动文件,避免影响 Python 字节码缓存。
  - 验证:同一份内容间隔两秒重打两次 —— 新方式指纹完全相同,旧方式两次都不同;新旧解包后逐文件内容摘要一致(只改元数据,内容零变化)。
  - **生效边界(如实说明)**:上一版的部件是用旧方式打的、无法追溯重现,所以**升级到本版仍是一次全量下载**;从本版升级到下一版开始,星历、Python 运行时、Java 运行时、玄学史资料等稳定部件(合计约 555MB)会被真正复用,增量只需下载约 135MB。

- 工程加固(用户看不见但决定「以后还会不会再犯」):
  - 懒加载边界收敛成单一实现:其中的「空模块自愈」是更新中途换包时不白屏的关键防线,此前它只存在于一处,组件内另写一份就会丢掉它。
  - 新增五道自动护栏,其中主锁会**自动抓取全部页面**做依赖图遍历 —— 以后任何新写的页面若把重引擎压进加载路径,提交前就会被拦下,不需要有人记得来更新清单;另一道直接检查「启动那一批实际拉了哪些包」,专防上面那种「代码全对但产物出卖你」的隐形通道。

- 界面细节(承 v3.6.1 后续):标题栏的四个悬浮层此前会弹到窗口外或越过右边界(提示条只剩一个箭头、用户菜单「管理命盘」只剩「管理」),已全部修正展开方向。
